There are two common ways. The safer one for zero downtime is:

**Recommended method (point the domain first, transfer later if you want)**

1. In Hostinger, note the nameservers they give you (or the A record IP).
2. In Squarespace → Domains → your domain → DNS settings, change the nameservers (or A record) to point to Hostinger.
3. Wait 24–48 hours for the change to fully propagate. During this time your old Squarespace site stays online until the DNS fully switches.
4. Once the domain is pointing to Hostinger and your new site is live, you can optionally transfer the domain registration itself later (unlock in Squarespace, get the EPP/auth code, start transfer in Hostinger). The transfer itself does not cause downtime if DNS is already correct.

**About 301 redirects**  
A 301 is a permanent “this page has moved” instruction.  
You only need it if:
- You change the domain name itself, or  
- You change the URL structure of pages (e.g. `/old-page` → `/new-page`).

If you keep the exact same domain and the same page URLs, you do **not** need 301 redirects when simply moving hosts. Search engines will notice the new server on their own.

#### more details about phase 2
What a straightforward Hostinger + Node.js + Express architecture looks like for your content
Hostinger (especially their VPS or Cloud plans) can run a Node.js app directly. A typical, maintainable stack for stories / images / comics / videos is:
text[User]
   ↓
[Hostinger VPS or Cloud]
   ├── Nginx (reverse proxy, SSL, static file serving, rate limiting)
   ├── Node.js + Express (API + server-rendered or API-driven pages)
   ├── Media storage options:
   │     • Local disk (simple, fine while small)
   │     • or Object storage (Hostinger’s own, Cloudflare R2, Backblaze B2, AWS S3)
   └── Optional: Cloudflare in front for CDN, DDoS protection, caching
Concrete pieces:

Express app
Routes for stories (text or Markdown → HTML), comic page sequences, image galleries, video streaming or progressive download.
Static middleware or Nginx for serving uploaded images/comics efficiently.
Video: either serve files directly (with proper Range support) or use a simple HLS setup later if you need adaptive bitrate.
Authentication / age-gate / paywall logic lives in Express (session, JWT, or cookie-based).

Media handling
Upload endpoint that stores files on disk or pushes to object storage and records metadata (title, tags, chapter order, etc.) in a database (SQLite to start, Postgres/MySQL later).
Generate WebP/AVIF variants or multiple resolutions on upload (sharp is the usual Node library).
Serve images and comic pages with caching headers; videos with proper content-type and range support.

Frontend
Can be server-rendered with Express + a simple templating engine, or a separate static/SPA frontend that talks to your Express API.
Lazy-loading images and comic pages is still a good idea for performance, but it is an optimization, not an evasion tactic.

Deployment on Hostinger
VPS plan → install Node, use PM2 or systemd to keep the process alive, put Nginx in front.
Or use their Node.js application hosting features if available on the plan you choose.
Point your domain, enable free SSL (Let’s Encrypt via Hostinger or Certbot).

Optional but useful additions
Cloudflare (free tier) in front for CDN caching of static assets and basic protection.
Database for metadata, user accounts, purchases, reading progress.
Background jobs (BullMQ or similar) for video processing / thumbnail generation if you grow.


This keeps everything under one provider and one domain, which is simpler to operate, cheaper at small scale, and easier to debug. If Hostinger’s policy later becomes a problem for your specific material, you can still migrate the same Node/Express app to another VPS provider with minimal changes.
